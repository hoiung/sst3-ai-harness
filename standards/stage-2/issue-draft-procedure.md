## Procedure

Create `/tmp/issue_draft_<topic>_<date>.md` FIRST. Do NOT create the GitHub issue yet.

**Process**:
1. Read the `/tmp` research file from Stage 1 AND run `python3 $SST3/check-stage1-research-fields.py /tmp/research_<topic>_<date>.md` exit 0 BEFORE proceeding. A failure is a hard block, never a silent workaround: fix it at source in Stage 1 until `graph_applicable` + `invoked_skill` + `skill_canonical_files` are declared. Usual causes: backtick-wrapped values (use unstyled YAML `graph_applicable: false`), enums outside `false | hybrid | true`, YAML inline comments in scalars. **Pre-dispatch sub-checks (AC 3.2/3.16):** (a) operator-state — if the symptom is 'X stopped working' / 'silent failure of Y', grep `.<X>_state` files / journalctl Stopped entries / UI-toggle audit comments before dispatching; (b) equivalence trace — for every equivalence claim, trace the consumer one level past the stated producer and cite the exact transform line; (c) body-size — <!-- c4:T04 --> a draft expected past ~50K chars is created as a stub then filled with `gh issue edit --body-file` (`gh issue create` caps at 65,536 chars), planned at Stage 2; (d) comment-walk — walk issue #N comments through <date> and stamp the frozen-scope file with the walk date; (e) JBGE-knob gate — for every new knob/constant with no current-problem evidence, mark `JBGE-DEFERRED` with a trigger condition; (f) implementer self-containment — verify a verbatim User Brief blockquote is present, no /tmp-only references; (g) cross-repo AP#22 — grep the draft for `cd <other-repo>` patterns and confirm AP #22 compliance + a pre-flight sentinel per downstream phase; (h) voice-mirror prerequisite — for any voice-guarded deliverable in a repo other than voice-doc-repo-doc-repo/hoiboy-uk/voice-staging, check whether the target repo appears in `SST3/drift-manifest.json` mirror-consumer list for the voice-scanner scripts (`check-iamhoi-wrapping.py`, `check-ai-writing-tells.py`, `voice_rules.py`); if not, add an AC 0.x to vendor the voice-scanner trio via `propagate-mirrors.py` before writing voice-gate verify commands. For an issue framed by a symptom word (duplicate/mismatch/conflict/drift), state in the draft the INVARIANT the symptom violates and probe for ALL its violations, not only the named one. **Char-budget discipline:** re-measure with `wc -m` (chars, not `wc -c` bytes) after every edit round and compute each Stage-3 fix's net char delta before applying the batch, against the ~262K edit ceiling; scope never moves into comments, where checkbox close-out cannot tick it. If the operator described ONE task, ask them 'one issue with phases, or split into N?' before drafting; never auto-split on subsystem/architecture grounds without sign-off.
1a. **Skeleton-first authoring (AC 3.5):** copy the full `issue-template.md` skeleton to `/tmp/issue_draft_<slug>.md` FIRST; fill scope into the skeleton — do NOT author a scope-only file and merge later. <!-- c4:T44 --> Write Expected Behavior from the brief before reading any findings; findings extend the operator's brief, never replace it.
1b. **Graph scope-completeness recipe** (structural-code topics in supported languages — see playbook "Stage-Mapped Recipes" Stage 2 section): for every function/hook/class named in the scope, run `bash $SST3/sst3-code-callers.sh <symbol> <lang>` and compare the count to what Stage 1 research claimed. More call sites than research flagged = expand scope. For every "X doesn't exist" claim, run `bash $SST3/sst3-code-search.sh '<pattern>' <lang>` (literal identifier when embeddings unavailable). Record every query + target + count + one spot-check file:line in the draft's References section. Skip if topic is semantic / non-code / one of the 12 subagent-only moments. **Citation freshness (AC 3.4):** for every `<doc-file>:<line-N>` reference in the draft, run `grep -n '<key term>' <file>` and confirm the content at that line matches the cited topic; record the grep output in References. For every ordinal/count assertion (N of M files, N entries, X/Y fixtures), compute current N and M from raw source and record the verification command output. <!-- c4:T11 --> Every clean verdict or figure recorded in the draft states the set and commit it was measured over, diffed against an independently enumerated target set; a self-referential count or size in the Issue body is re-derived at the moment it is stated, after every edit.
1c. **Scope decomposition (AC 3.11):** (A) for each sub-issue MERGE, list the component scopes, confirm each has a destination AC, and preserve phase-ordering (1a/1b/1c) where sub-scopes have implicit sequencing; (B) for each sub-issue DROP, decompose the dropped sub-issue into its component scopes and confirm each is deferred-with-trigger or absorbed into a surviving AC; (C) for any multi-axis goal (SEO, architecture, compliance), decompose into BOTH axes as separate scope dimensions before writing ACs; (D) for any new knob/mechanism with no documented current-problem evidence, mark `JBGE-DEFERRED` with a trigger condition rather than scoping it as an AC.
2. Read `../../templates/issue-template.md`. Follow the template EXACTLY. Every section is mandatory:
   - PREREQUISITE CHECKPOINT (6 principle checkboxes)
   - Problem/Goal
   - Acceptance Criteria (phased, phase-checkpoint notes between phases)
   - Engineering Requirements (Type Contracts, Schema Contracts, Config Traceability)
   - Quality Mantras (VERBATIM — see below)
   - Cleanup Requirements (Code Hygiene + File Housekeeping)
   - Context + References
2a. **Voice canonical-anchor pre-draft step (AC 2.5):** for issues with operator-voice content (`invoked_skill ∈ {blog, voice-doc-repo, consulting}`), compile the operator's canonical opening lines across all live channels and paste them verbatim into the draft front-matter as `canonical_voice_anchors`; any new prose must preserve the semantic frame of at least one anchor.
3. Write ALL before/after illustrations. Show what exists NOW vs what it will look like AFTER so we can compare after implementation. These are mandatory for every change — code, config, behaviour, UI. **Truth-table temporal axis (AC 5.5):** for any truth table in an AC, add a Temporal axis row (mid-flight | terminal) and enumerate all parameter modes (`full_history=True/False`, etc.) — a table without the mid-flight-vs-terminal axis silently assumes terminal-only. <!-- c4:T43 --> A visual or computed-definition deliverable (chart, derived metric, new term with a formula) is rendered from live data and shown to the operator before Stage 2 closes; prose describing it does not count.
3.5. **Author self-check block (AC 2.1) — MANDATORY before any subagent dispatch.** Run the full pre-dispatch self-check catalogue in `../../standards/stage-2/pre-dispatch-self-checks.md`: (a) placeholder sweep → zero hits; (b) scope-narrowing; (c) min-v1 sketch before research-driven extensions; (d) template-structure check; (e) JBGE per-AC necessity; (f) budget sanity (`wc -l` before codifying any line-count budget); (g) reuse-before-new (AP #10 at draft-time); (h) cross-repo state (`ls`/`grep`/`gh` against repo Y for every "existing X in repo Y" claim); (i) multi-option AC classification (evidence-supported→force / destructive-irreversible→operator-pre-consent / policy-level→defer); plus item (j) author-time source-read gate (Read cited file:line into Before blocks, `sed -n '<line>p'` verbatim quotes, re-grep symbols, re-execute carried predicates, read reuse targets' full body); plus shape-gated item (k) multi-root script file-availability (for a bootstrap/installer script resolving files from >1 root, establish the step's run-order position and identify which root — pre-clone staged / post-clone repo / operator-invoked staging dir — makes the file present at THAT step before writing the import path); plus (l)–(t) — full text in the catalogue. Zero unresolved items before dispatch.
4a. **PRE-DISPATCH FIRST PASS — placeholder/stub grep sweep (Theme 5, #477 AC 2.1)**: BEFORE dispatching Layer-1/2 audit subagents (step 5), run `grep -E 'placeholder|stub|\bTODO\b|if needed|nice-to-have|could be' /tmp/issue_draft_<topic>_<date>.md`. For each hit: replace with concrete spec OR document explicit out-of-scope-with-rationale (no "we might do this later" wording). **Zero hits required before subagent dispatch.** Rationale: subagents that audit a draft full of placeholder/stub language will mirror the placeholders forward as "captured scope" instead of flagging them as gaps — the audit becomes a rubber-stamp. **Finding-to-AC traceability gate (AC 2.3):** (1) extract every Fn AND every Gn from the Stage-1 research file; build a two-column table [finding_id | planned_AC_id]; every row must carry an AC number or explicit `out-of-scope: <rationale>` — gaps with neither block dispatch; (2) walk every imperative phrase ('AVOID', 'MANDATORY', 'required', 'must') in every finding and bind each to a specific AC at sub-element level, not headline level; (3) for every operator-supplied artifact name referenced in a draft AC, run `grep -rl <name>` in the repo — zero hits → AskUserQuestion before writing the AC; (4) if Stage-1 §3 uses unverified-assumption phrasing ('presumably', 'assumed', 'expected'), flag each as an open question to resolve in-draft, not carry forward; (5) confirm every cluster file and reserved AP number the draft announces maps to a creating AC, and every peer doc it references to a cleanup AC (not Fn/Gn findings, so the table misses them).
4b. **POST-CORRECTIONS SECOND PASS — same grep sweep (Theme 5, #477 AC 2.2)**: AFTER Layer-2 corrections applied + amendments integrated (step 7), re-run the same grep sweep. **Zero hits required before declaring Stage 2 complete.** Rationale: Layer-2 corrections are inserted via copy-paste from subagent recommendations, which can re-introduce "could be / if needed / nice-to-have" wording even after Pass 1 was clean. Record hit→fix counts in the per-stage feedback file (`SST3-metrics/leader-feedback/feedback-<repo>-<issue>.md` Stage 2 `worked` field). For a public-repo scrub issue or voice-guarded artefact, re-run the leak-scan / em-dash + path-literal scrub after every manual Edit to the draft, preferring an oracle exit code to a literal-token grep. **Post-corrections resync (#555 Ralph r3):** after applying any batch of draft corrections — or inserting an AC that adds new files/languages/commit-units — re-read and resync in the SAME pass: (a) the SUMMARY layers end-to-end; (b) the Anti-Bias file list, the commit-atomicity note, and the File-Housekeeping created-files list. <!-- c4:T34 --> Draft corrections and splits are edited by structural anchor (line-anchored equality or heading regex), asserting exactly one match of the old text, never by character offset or bare substring.
4c. Quality mantras — include VERBATIM in the issue scope (copy exactly, do not paraphrase):
   - No inefficiencies, fix optimisation opportunities
   - Reliable and robust (not prone to breakage or failing)
   - Dedupe duplicate codes
   - No bottlenecks
   - Runs super fast and safe
   - No memory leaks using preventions
   - Follows STANDARDS.md
   - No false positives — everything real gets fixed
   - No such thing as high priority or low priority — all must be fixed

4d. **Mirror-lane mapping (AP #9)**: build the vendored / unmirrored / no-manifest table by parsing `SST3/drift-manifest.json` first, never from file paths. 4e. **AC verifiability sweep (Theme 10, #477 AC 2.9)**: before dispatching the layer-1 swarm (step 5), the author reads each AC checkbox and confirms a falsifiable verification command/method exists (binary pass/fail). Rule lives in STANDARDS.md "Workflow Validation Gate" → "AC Verifiability — pre-Stage-3 sub-gate" + issue-template.md "AC Verifiability Gate" subsection. ACs without falsifiable verification get rewritten OR moved to "Items Not Fixed" with rationale BEFORE subagent dispatch — do NOT pass unfalsifiable ACs into the swarm. Pre-swarm rewrites are cheaper than post-swarm rewrites because subagents anchor on whatever scope they receive. <!-- c4:T08 --> A verify runs through the enforcing gate (the hook, CI job or script that refuses the change, not a grep beside it) on artefacts that exist by the end of its own phase; first check the gate's empty-input exit code (exit 0 on no input passes a verify fed nothing). An arithmetic or unit claim gets a verify pinning the expression plus a mutant (if defaults zero the term, say so and pin the line); a verify's pre-fix run is read-only (it writes no report, cache or baseline); prefer presence or kind assertions over counts when the producer's yield depends on the environment. <!-- c4:T12 --> A build-dependent predicate (rendered page, served header, bundled asset) is measured on built or served output, never source, with close-out's own command and its build flags audited (a drafts-included or dev-mode build is not what ships). <!-- c4:T22 --> A greenfield draft also dry-runs every verify against a mocked post-fix tree (a scratch copy with the intended files stubbed in). <!-- c4:T55 --> <!-- c4:T56 --> <!-- c4:T57 --> Before the discriminability sweep, re-read the operator noun behind each AC ('every consumer') and confirm the AC asserts it, not a nearby one; a verify's explicit file list becomes a repo-wide derivation plus named exemptions; a claim about a named field (a `REQUIRED` set, an enum) pastes the literal contents of a cited field; and decompose a path-filter headline count member by member before quoting it (the pattern also matches fixtures, generated files, archives). <!-- c4:T58 --> An AC introducing a runtime component lists its full provisioning input set, one provisioning AC per item. **Two required sub-angles (AC 2.2):** (a) **Falsifiability** — for each verify command, mentally simulate a deliberate FAIL state; if the command passes in BOTH the pass and fail states, flag it as toothless and rewrite; (b) **Discriminability** — reject bare-substring greps where an exact-match pattern is available; reject narrative phrases ('output reports', 'reads', 'expects', 'appears to', 'should show') as verify text; an 'add a structural/regression test' AC's verify MUST be a PAIR — `pytest <file>` exit 0 AND `grep -c '<new assertion string>' <file>` ≥ 1 (exit-0 alone proves the file runs, not the NEW contract). Author-time preconditions: (c) when a script is named as a verify command, confirm it has an entry-point (`__main__` / argparse / shebang + exit-code contract) before writing it in; (d) when a gate is named as a verify command, confirm the gate's scope rules (exempt-path prefixes, mode skip matrix) admit the file under test; (e) any AC whose only verify is a live external web service or launch-day manual action must ALSO carry a CI-side local gate (parse / grep / exit-code); (f) a new hard-gate AC (BLOCK/FAIL-on-condition) must honour every exception/escape-hatch AC in the draft, checked in the same authoring pass. **`command-resolves` sub-check (AC 3.1):** for every Verification clause, (a) dry-run the named binary/path/flag from the target repo's worktree root; (b) replace `grep -P` with `grep -E`; (c) classify vacuous-truth patterns (`all()`/`any()` over empty iterables, Promise without await, grep matching comment-only lines). **AC design-quality checks (AC 4.5):** (1) dry-run each AC verification command against the current PRE-FIX tree and confirm it returns the FAIL value (non-zero exit / the pre-impl count); a verify that passes pre-fix is vacuous and MUST be re-scoped (line-range / exact-pattern / call-site anchor) before dispatch — **mechanise this dry-run with `python3 $SST3/check-ac-discriminability.py <draft.md> --tree-root <repo-root>` (dotfiles#528 AC 6.4): it flags grep/wc/`test` verifies that already pass against the pre-fix tree (exit 1 on any vacuous one) and, post-#555, also hard-flags ALT-AND-RISK / AWK-RANGE-COLLAPSE / FIXTURE-FAIL constructions per the gotcha catalog (g)/(h) below, plus (#577) a TEMPLATE-TAIL-VERBATIM draft whose copied template tail still has every fill-in slot unfilled, and a CLAIM-LIST-HAND-WRITTEN / CLAIM-LIST-STALE AC Verifiability Gate section (paste the output of `--claims`, generated from the finished draft, between the `<!-- ac-gate:generated -->` markers; never hand-write which classes the draft is free of), with a non-blocking `sed -n Np` LINE-ANCHOR advisory; narrative / live-web / script-exec verifies are SKIPPED and remain this manual author step**; run `find tests/ -type d` and verify all cited paths exist; (2) for each AC, ask whether the machine-enforcement gate alone is sufficient to prevent the risk — split any AC containing operator-runtime gates into runtime-independent + runtime-dependent sub-ACs; (3) after any phase-rewriting implementation commit, identify every earlier AC whose satisfying text lived in that block and re-run its verification command (block-rewrite regression check); (4) before posting the Gate-1 close-out checkpoint, re-run each AC being marked complete — do not rely on in-session memory of test results. **(g) verify-command gotcha catalog:** (1) an 'N items present' claim needs a per-item grep with its own count — never one aggregate, and never a count over an OR-alternation (`a|b|c`), which one branch can satisfy N times; (2) plain `grep` is BRE: `\|` alternates, bare `|`/`(`/`)` are literal; (3) an awk `/start/,/end/` range self-collapses to single lines when the start line also matches the end pattern; (4) an 'X appears only at Y' claim needs `grep -rniE` over the WHOLE tree, every hit read; (5) a NEGATIVE grep (`== 0` after a removal) must also be simulated against the mocked POST-FIX state, where a retirement comment or same-named stub re-trips it; (6) <!-- c4:T07 --> <!-- c4:T18 --> <!-- c4:T28 --> a citation, line number or count is produced against the exact target (the real file at the claim's ref, never a window, variant or repo prose), its matching lines printed and read before recording; an absence is asserted with `grep -c` → `0`, never truncated output (`| head`, a pager, a clipped tool result); `grep -c` counts LINES, so on a single-line or minified file use an occurrence-aware extractor (`grep -o … | wc -l`, a parser). A remediation hint, error message or generated command shown to the operator is executed, not string-compared. **(h) construction edge-cases:** (1) a multi-line/block construct needs a block-scoped extractor (awk range with DISTINCT start/end patterns, or `grep -A`); (2) a removed-token grep needs word-boundary + comment-line exclusion, re-verified post-edit; (3) a shape-literal verify carries an 'or a named-constant/equivalent form' escape clause; (4) prefer a content-anchored grep to `sed -n Np` (earlier ACs shift lines); (5) a 'runs in CI' AC asserts collection scope (`pytest --collect-only | grep <test>`), not just a green run; (6) if a scanner's input-set can be incomplete, prefer a closure-style verify (`advisories == 0`) to enumerated targets. An AC banning a code construct prefers as PRIMARY verify a unit-test invariant on the single chokepoint every legitimate use routes through (allowlist const / helper fn); its source grep is only a secondary tripwire (new call sites bypass it). For an AC turning an exact-match key/JOIN into a bucketed/truncated/externally-computed value, or updating a UNIQUE column from an external value, check whether >1 source row can map to one target and add a collision-tolerance AC (dedup / NOT-EXISTS guard / catch+fall-through) in the same edit. Draw the writer/reader data-flow DAG before writing any AC that auto-recomputes or re-runs a pipeline. **Char-budget cross-check (#555 Ralph r3):** the sweep re-measures the post-edit draft with `wc -m` against the ~262K `gh issue edit` ceiling (step 1's Char-budget discipline) — its own rewrites are edits too.
